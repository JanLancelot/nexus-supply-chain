# Diagnostic collection measurements

These are local collection experiments from 26 September 2026, not production
reliability statistics. The tool gathers evidence; an operator still diagnoses
the incident and verifies recovery. See [the scope and study
protocol](diagnostics.md) before interpreting the numbers.

## Three paired machine measurements

Command: `python3 bin/benchmark-diagnostics.py --project nexus-local --iterations 3`.
The existing eight-service local stack remained running throughout. No faults,
application requests, recovery actions or external notifications were generated by
the diagnostic tool. The measurement completed at **01:32:37 UTC**.

| Trial | Order | Five separate commands | One combined command |
| --- | --- | ---: | ---: |
| 1 | Separate then combined | 1.232 s | 0.334 s |
| 2 | Combined then separate | 1.198 s | 0.313 s |
| 3 | Separate then combined | 1.146 s | 0.293 s |
| Median | | **1.198 s** | **0.313 s** |

All eighteen invocations returned complete collections. Both modes collected the
same five sections with identical fixed queries, projection and log bounds.
Separate mode discovered and validated the project five times; combined mode did
so once. Thus these numbers mainly quantify repeated command and discovery
overhead. Each observation occurred at a different time. The local Docker host
was also used for development; load and caches were not controlled. This is not
an application performance benchmark.

Runtime: Darwin 27.0.0, arm64, Python 3.13.14, Docker client/server 29.5.3.
Diagnostic implementation: commit `962c7c0`; source SHA-256
`fff94c55810d44f6e2f1d3aa936c555bcb3694b8288b9c04a1bddbdedf6f2ed8`.

Private evidence is retained in
`.artifacts/diagnostics/benchmarks/20260926T013233Z-bf6cdf36/`: the benchmark JSON
and Markdown, all individual reports, command exit codes, query expressions and
source hash. Those generated reports are deliberately excluded from Git and
Docker builds. The table above is a reviewed aggregate, not a raw diagnostic
export.

## A real degraded collection

During development of the isolated incident harness, a backend stop in disposable
project `nexus-drill-fb5d4ef85880` was observed at **01:31:07 UTC**. The diagnostic
command completed in **0.704 seconds**, exited `1`, and preserved the following:

- Backend container `exited`, exit code `143`; five other required services were
  running. The six-service drill intentionally has no Grafana/database pair.
- Backend scrape target `down`, with a scrape error present. The target URL and
  error text were omitted.
- `NexusBackendDown` was `pending`; `NexusWatchdog` remained `firing`. Pending
  state is evidence of detection, not evidence of a delivered page.
- All eight application metric queries returned explicit missing-metric errors.
  None were converted to zero or interpreted as healthy.
- Container, target, alert and bounded log-summary collection remained complete;
  only the metric section was partial. Log messages were absent from the output.

Private report: `.artifacts/diagnostics/20260926T013107Z-594ecec9/report.json`
and its companion Markdown file. This was a real development-run failure
observation, not the final incident-response exercise. The harness was later
stopped and cleaned up for unrelated drill-measurement corrections. This
collection does not establish notification latency, successful recovery or MTTR.

## What remains unmeasured

No human manual investigation was timed. The tool reduces a defined five-command
collection workflow to one invocation, but neither the 0.885-second median
machine-time difference nor that command reduction establishes saved human
minutes. Use the paired human-study protocol to measure hands-on time, conclusion
accuracy, omissions and retries during comparable disposable incidents before
making a toil-reduction or recovery-time claim.
